# PLAN. Этапы реализации

Каждый этап маленький, самодостаточный и закрывается тестами, которые доказывают,
что этап готов. Порядок важен: ядро сначала, потому что там вся сложная логика
и Telegram для неё не нужен.

## Этап 0. Каркас (готово)

Структура пакетов из SPEC.md 5.1, заглушки во всех модулях, два теста
(smoke и граница `core`), CI, `.env.example`, `.claude/settings.json`.

Готово: `uv run pytest`, `uv run ruff check .`, `uv run ty check` зелёные.

## Этап 1. Ядро: recurrence и reminders

Самая сложная логика предметной области, без Telegram и без SQLite.

- `core/recurrence.py`: `next_occurrence` (ежегодное повторение, правило
  29 февраля), `age_on` (возраст/годовщина).
- `core/reminders.py`: `due_at_utc` (локальная дата → смещение → время суток →
  локализация → UTC, сдвиг при несуществующем локальном времени),
  `materialize_for_event` (напоминания на 400 дней вперёд, без напоминания
  самому себе о своём дне рождения).
- `core/ports.py`: `Clock` уже объявлен, тесты подменяют его вручную
  (простой класс с фиксированным `now()`), без реальных часов.

Тесты (`tests/core/test_recurrence.py`, `tests/core/test_reminders.py`):

- 29 февраля в невисокосный год даёт напоминание на 28 февраля, в високосный —
  на 29 февраля (критерий приёмки 4).
- Два получателя в разных часовых поясах для одного события получают разные
  `due_at_utc`, оба соответствуют 09:00 по своему времени (критерий 5).
- `due_at_utc` пересчитывается при смене даты события/пояса/смещений без
  изменения уже прошедших напоминаний (критерии 6, 7).
- Несуществующее локальное время (перевод часов) сдвигается вперёд до
  ближайшего существующего момента.

Готово: перечисленные тесты проходят, `core` по-прежнему ничего не знает про
внешние слои.

## Этап 2. Ядро: родство

- `core/relations.py`: базовые рёбра, заглушки, слияние, второй родитель,
  ограничение на двух родителей, вывод родства обходом графа (глубина ≤ 3).
- `core/texts.py`: `relation_word`, `reminder_text` с учётом пола.

Тесты (`tests/core/test_relations.py`, `tests/core/test_texts.py`) закрывают
критерии приёмки 17–23: брат/сестра при известном и неизвестном родителе,
слияние заглушки, второй родитель, отказ третьему, глубина родства.

Готово: все критерии 17–23 проходят на чистых данных в памяти, без хранилища.

## Этап 3. Ядро: сценарии (services.py)

`create_family`, `add_person`, `issue_invite`, `accept_invite`, `add_event` —
поверх `relations.py`, `reminders.py`, `texts.py` и портов-протоколов
(`FamilyRepo`, `PersonRepo`, `AccountRepo`, `EventRepo`, `InviteRepo` — фейковые
in-memory реализации в тестах).

Тесты закрывают критерии 14–16, 24–27: напоминание о дне рождения сразу при
добавлении человека, не себе, приглашение привязано к записи и одноразовое,
отказ не-владельцу на изменение дерева.

Готово: сценарии проходят на in-memory реализациях портов, `core` всё ещё
не знает про SQLite.

## Этап 4. Storage: SQLite-адаптеры

- `storage/db.py`: `connect` (PRAGMA), `apply_migrations`.
- `storage/migrations/000N_*.sql`: полная схема из SPEC.md 5.3.
- `storage/repos.py`: реализации всех протоколов `core/ports.py` поверх
  `asyncio.to_thread`.

Тесты гоняют те же сценарии из этапов 1–3, но с реальным SQLite вместо
in-memory реализаций (общие фикстуры, разные репозитории). Отдельный тест на
критерий 28: миграции применяются по порядку, повторный старт их не повторяет.

Готово: одинаковые поведенческие тесты проходят и на in-memory, и на SQLite.

## Этап 5. Scheduler: тик и материализация

- `scheduler/tick.py`: claim → send → mark, обработка 403/сетевых ошибок/
  `attempts`, просрочка в `missed` (критерии 8–13).
- `scheduler/materialize.py`: суточное задание.
- `scheduler/setup.py`: сборка `AsyncIOScheduler` (добавляется зависимость
  `apscheduler` через `uv add`).

Тесты подменяют `Clock` и `Notifier`, гоняют тик несколько раз подряд без
`sleep`, проверяют идемпотентность и переходы статусов.

Готово: критерии приёмки 8–13 проходят.

## Этап 6. Telegram-слой

- `telegram/notifier.py`: `TelegramNotifier` поверх aiogram (добавляется
  зависимость `aiogram` через `uv add`), перевод 403 в `RecipientBlocked`.
- `telegram/routers.py`, диалоги на машине состояний: создание семьи,
  добавление человека, приглашения, выбор часового пояса и текущей семьи.
- `telegram/bot.py`, `__main__.py`: сборка зависимостей, длинный опрос.

Тесты роутеров — без сети, с фейковым апдейтом aiogram. Критерий 3 (нет
`BOT_TOKEN` → понятная ошибка) уже покрыт `config.py` на этапе 0, здесь
добавляется тест на реальный старт `__main__`.

Готово: бот поднимается локально с тестовым токеном, диалоги проходят вручную.

## Этап 7. Сквозной сценарий

`tests/e2e/test_reminder_flow.py` из SPEC.md 9: часы и транспорт подменены,
семья с двумя людьми, один тик, ровно одно сообщение с ожидаемым текстом.

Готово: `uv run pytest tests/e2e/test_reminder_flow.py -v` печатает `1 passed`
меньше чем за секунду.
